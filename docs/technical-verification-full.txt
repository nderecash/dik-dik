===== keyword-recognizer =====
VERDICT: PARTIAL. The API exists and is not deprecated in code (CONFIRMED). Its reliability on an ordinary Windows 11 machine is REFUTED (no evidence found, and strong counter-evidence). The mic-coexistence assumption is UNVERIFIED, so per your skeptical default, treat it as REFUTED. The plan as written is not safe to build on.

DETAIL:
1. DOES IT STILL EXIST IN UNITY 6.x? Yes, confirmed.
Namespace UnityEngine.Windows.Speech. It is core engine code, not a package: it lives in UnityCsReference at Runtime/Export/Windows/Speech.cs and Speech.bindings.cs, bound to the native header PlatformDependent/Win/Bindings/SpeechBindings.h. It compiles into UnityEngine.CoreModule, so nothing to add to Packages/manifest.json. I checked the current C# reference source for [Obsolete] attributes on PhraseRecognizer, KeywordRecognizer, GrammarRecognizer and DictationRecognizer: there are none. I also grepped the live Unity 6.5 scripting reference page for KeywordRecognizer and it contains no instance of "obsolete", "deprecated" or "removed". One "Legacy" string appears in the page chrome; I could not extract its context, so I will not claim it is an API status marker either way. Nothing in Unity 6.5 release notes indicates removal.

2. WINDOWS REQUIREMENTS. This is where it falls over.
The Unity 6.5 docs still say, verbatim, "Keyword recognizer is currently functional only on Windows 10." Unity has never updated that sentence for Windows 11. PhraseRecognitionSystem carries the same restriction and exposes isSupported precisely because the platform may not support it.

Meanwhile Microsoft's own deprecated-features list (entry dated December 2023, page last updated Feb 2026) says: "Windows speech recognition is deprecated and is no longer being developed. This feature is being replaced with voice access." The handover landed on Windows 11 22H2 and later in September 2024. I looked for a Microsoft statement that the underlying APIs (SAPI, System.Speech, Windows.Media.SpeechRecognition) survive that removal intact. There is none. The closest is a Microsoft Q&A thread where a Microsoft support specialist answered the exact question with "there will be a gradually migration happening because that is the nature of software industry", which is not a commitment.

The documented failure mode is not a clean exception you can plan around, it is exactly the silent-death case you were worried about. PhraseRecognitionSystem.isSupported returns false and the KeywordRecognizer constructor throws UnityException: "Speech recognition is not supported on this machine." MRTK issue #7498 exists solely because MRTK kept trying to start recognizers on machines where this happens, producing 328 log lines per test run. The dependency is on the OS speech platform being installed and on a speech language pack matching the display language. SpeechError also includes MicrophoneUnavailable, TopicLanguageNotSupported and NetworkFailure, so it can fail after a successful start too.

Note the split: KeywordRecognizer maps to a local list constraint, so it does not need the "Online speech recognition" privacy toggle. DictationRecognizer does, and fails with SPERR_SPEECH_PRIVACY_POLICY_NOT_ACCEPTED (0x80045509) when it is off. So the privacy toggle is not your risk. The missing speech engine and language pack is.

Evidence for Windows 11 specifically: one Unity Discussions thread from 1-2 March 2026 tagged Unity 6.2, "Keyword Recognizer on windows 11". A community member replied "it should still work on Windows 11 as the Speech SDK is backward compatible." That is a guess, not a test. No Unity staff replied. Notably the person who asked said they had already switched to Whisper. That is the entire public evidence base for Windows 11. It is not enough.

3. THE CRITICAL QUESTION: CAN KEYWORDRECOGNIZER AND UNITY'S MICROPHONE CLASS SHARE THE MIC?
No authoritative source answers this. Not Unity's docs, not Unity staff, not Microsoft Learn, not the Unity issue tracker. I searched specifically for it and came up empty. Anyone telling you it definitely works or definitely does not is guessing.

What is actually documented is a different constraint that is easy to mistake for this one. Microsoft Learn states: "Dictation and phrase recognition can't be handled at the same time. If a GrammarRecognizer or KeywordRecognizer is active, a DictationRecognizer can't be active and vice versa." That is a constraint inside Unity's own speech stack. It says nothing about UnityEngine.Microphone.

The architectural argument in your favour: Windows WASAPI shared mode allows multiple applications and multiple clients to capture the same endpoint concurrently. Only exclusive mode locks others out, and neither Unity's FMOD-backed Microphone nor the Windows speech stack opens exclusive mode. So it should work. But "should" from first principles is not verification, and your instruction was to default to REFUTED without clear evidence. So: unverified, do not build the instant-STOP design on it until you have run it yourself.

Relevant to this: I checked your project. C:\dev\dik-dik is on 6000.5.2f1 and already pulls com.whisper.unity (Macoron) at commit de9ce92ad4c5. Its MicrophoneRecord.cs calls Microphone.Start at line 262 and owns the device for the whole session. So the conflict, if it exists, is guaranteed to bite: whisper.unity holds the mic open continuously.

4. ALTERNATIVES. The best one is already in your project.
whisper.unity ships an energy-plus-frequency VAD (AudioUtils.SimpleVad) that MicrophoneRecord runs on a 100ms tick (vadUpdateRateSec = 0.1f, vadThd, vadFreqThd, OnVadChanged event). That gives you a genuine sub-100ms "someone is speaking" signal for free, off the same single Microphone.Start, with zero mic contention.

whisper.cpp upstream already solves the small-vocabulary case: examples/command has a guided mode where you pass a command list and, in the project's own words, "the transcription will be guided to classify your command into one from the list." That is your four words exactly.

The latency lever is audio_ctx, and whisper.unity exposes it as WhisperParams.AudioCtx (WhisperParams.cs line 306). Default is 1500, which makes the encoder chew a full 30s window regardless of how much audio you fed it. whisper.cpp's own discussion #297 documents the tradeoff and says the option "is suitable for the stream and command examples in this repo", with the working formula (audio_length/30)*1500 + 128, and warns the decoder starts to glitch if you stray too far from the 30s training window. Issue #1855 reports roughly 3x speedup on short clips.

System.Speech is the worst of the three options you listed. It is not in Unity's .NET profile, needs the desktop .NET Framework assembly referenced by hand, is Mono-and-Windows-only, and it binds to SAPI 5.4 / the Microsoft Speech Recognizer, which is the exact engine Microsoft deprecated. Same OS risk as KeywordRecognizer plus more integration pain.

Windows AI APIs speech recognition is not a fit either: it requires Windows 11 24H2 build 26100+, WinAppSDK 1.7.1+, and MSIX packaging with the systemAIModels capability declared. A Unity standalone build is not MSIX.

RECOMMENDATION:
Drop KeywordRecognizer from the critical path. Do not make the instant-STOP depend on it.

Build the fast path out of what is already in the project, on one shared Microphone.Start:

1. Keep exactly one MicrophoneRecord. Never call Microphone.Start twice. This removes the unverified mic-conflict risk entirely rather than betting on it.
2. Wire MicrophoneRecord.OnVadChanged as the instant gate. VAD onset fires within ~100ms. On onset, immediately apply a caution response (cut rover throttle, arm the stop). This is defensible HCI, not a hack: the rover reacts to "the operator is saying something" before it knows what.
3. Confirm with a second WhisperManager running tiny.en on a ~1s rolling slice of the same buffer, configured as a classifier: SingleSegment = true, AudioCtx around 256 to 384 (per the (audio_length/30)*1500 + 128 formula for ~1s), InitialPrompt seeded with "stop, go, left, right", greedy decode. Then fuzzy-match the output against the four words. Realistically this lands in the 100 to 300ms range on a desktop CPU, not sub-200ms guaranteed. Measure it, do not assume it.
4. Leave your existing full whisper context on the ~1.9s natural-speech path, unchanged.

If you still want KeywordRecognizer, add it strictly as an optional accelerator, never as the mechanism:
- Gate every use behind if (PhraseRecognitionSystem.isSupported), and wrap construction in try/catch for UnityException.
- Subscribe to PhraseRecognitionSystem.OnError and treat any SpeechError as permanent disable, not retry.
- The game must be fully playable with it off. Ship with it defaulted off.

Before any of that, run a 20-minute spike on your actual Windows 11 machine. It answers questions 2 and 3 at once, which no amount of further reading will:
- Log PhraseRecognitionSystem.isSupported at startup. If false, KeywordRecognizer is dead on your target hardware and the whole question is moot.
- If true, call Microphone.Start first, then start the KeywordRecognizer, and confirm both keep producing data for 60 seconds. Then reverse the order and repeat. Also check whether a running KeywordRecognizer degrades whisper's transcription quality, which is a subtler failure than an outright conflict.
- Record the result in the project docs so this does not get re-litigated.

One correction to the plan's framing: your project file C:\dev\dik-dik\Assets\Scripts\Producers\VoiceCommandProducer.cs already checks Microphone.devices at line 226, so there is an existing seam to hang the VAD gate on rather than adding a parallel system.

===== webgl =====
VERDICT: PARTIAL â€” Q1 confirmed with an important correction to the failure mode and the fix mechanism; Q2 REFUTED (both proposed guards are wrong); Q3 mostly REFUTED (Brotli is no longer an itch.io problem); Q4 confirmed (WebGL2 only) plus three concrete regressions/no-ops found in the existing build script.

DETAIL:
1. WHAT BREAKS, AND WHEN

It fails at BUILD time, not runtime, and not at C# compile time. The C# compiles fine. It dies in the Emscripten link step of the IL2CPP build with `undefined symbol: whisper_init_from_file_with_params` (and one line per bound function). Confirmed pattern: a native plugin with no WebGL binary produces `undefined symbol: <function>` at link (Unity Discussions "Unity WebGL and Native Plugins can't build"). Emscripten defaults to ERROR_ON_UNDEFINED_SYMBOLS=1, so the build stops.

Why, specifically in this project (verified on disk):
- C:\dev\dik-dik\Library\PackageCache\com.whisper.unity@de9ce92ad4c5\Runtime\com.whisper.unity.asmdef has `"includePlatforms": []` and `"excludePlatforms": []`. Both empty means every platform, WebGL included.
- Runtime\Native\WhisperNative.cs line 15-19: `#if (UNITY_IOS || UNITY_VISIONOS || UNITY_ANDROID) && !UNITY_EDITOR` -> `"__Internal"`, `#else` -> `"libwhisper"`. WebGL falls into the `#else` branch, so ~40 `[DllImport("libwhisper")]` declarations are emitted for a library that does not exist.
- The package ships Plugins/{Android,iOS,Linux,MacOS,Windows} and NO Plugins/WebGL. Nothing to link against.

Unity's Web manual only accepts `.a` (GNU archive of WebAssembly `.o`) since 2021.2, or legacy `.bc`. A Windows `.dll` is never a candidate; Web has no dynamic library loading, everything is statically linked, and the Emscripten version used to compile the plugin must match Unity's exactly.

Which exclusion mechanism is correct, in order:
- Plugin Inspector platform settings: NOT the fix here. The .dll/.so/.dylib meta files already restrict themselves to their own platforms, and the plugin binaries are not what the linker is complaining about. Worse, the package lives in Library/PackageCache, which is immutable, so the Inspector is greyed out and any meta edit gets wiped on reimport.
- `#if UNITY_WEBGL` around your own code: NECESSARY BUT NOT SUFFICIENT. It removes Assets/Scripts/Producers/VoiceCommandProducer.cs from the build, but com.whisper.unity.dll is still compiled and, being an autoReferenced package assembly whose MonoBehaviours (WhisperManager) are reachable, its DllImports still reach IL2CPP.
- Assembly definition constraint: THE FIX. `"excludePlatforms": ["WebGL"]` on the package's runtime asmdef. `WebGL` is the correct platform string (Unity's Assembly Definition file format reference uses it verbatim in its excludePlatforms example). includePlatforms and excludePlatforms cannot both be non-empty.
- To edit that asmdef you must first embed the package: copy Library\PackageCache\com.whisper.unity@de9ce92ad4c5 to Packages\com.whisper.unity. Unity then treats it as mutable and Package Manager stops resolving the git URL. This also pins a dependency that currently has no registry release. The existing comment at Assets\Editor\DikdikBuild.cs lines 74-84 already describes exactly this, and it is correct.

Note for later: whisper.unity's README lists WebGL as supported but links to issue #20, which was opened 2023-04-29, has no maintainer response and no PR. Treat WebGL as unsupported. One assumption in that issue is now stale: Unity 6.5's Web manual says the Microphone class is fully supported on Web given `Application.RequestUserAuthorization` and HTTPS hosting. Mic capture is no longer the blocker. The missing WebAssembly build of whisper.cpp is.

2. THE COMPILE GUARD

Both proposals are wrong.
- `#if UNITY_STANDALONE_WIN && !UNITY_EDITOR` compiles the code out of the Editor, so you cannot test speech in Play mode on your own machine. UNITY_STANDALONE_WIN tracks the active build target, and UNITY_EDITOR is true in the Editor, so the two together are never both satisfied while you are working.
- ENABLE_WINMD_SUPPORT is unrelated. It is the WinRT/Windows Runtime metadata guard for UWP/Windows Store builds. UnityEngine.Windows.Speech on desktop is not gated by it.

Correct guard: `#if UNITY_STANDALONE_WIN || UNITY_EDITOR_WIN`. UNITY_EDITOR_WIN reflects the Editor's host OS, not the build target, so the code compiles and runs in Play mode even with WebGL as the active target (Editor scripts compile against the Editor's own UnityEngine assemblies, which contain the type). In a WebGL player neither symbol is defined, so it is stripped.

KeywordRecognizer, DictationRecognizer and PhraseRecognitionSystem live in the UnityEngine.Windows.Speech namespace in UnityEngine.CoreModule. Unity's own scripting reference states the restriction plainly: "Keyword recognizer is currently functional only on Windows 10."

Practical note: this is currently moot. I grepped Assets\Scripts and the project uses whisper.unity only. There is no UnityEngine.Windows.Speech usage anywhere. Only apply this if you add a Windows-native fallback recognizer.

3. ITCH.IO IN 2026

Brotli is NOT a problem anymore. itch.io's own HTML5 docs: "If the filename ends with the extension .br then we'll assume that the content is Brotli compressed and the content-encoding will be set to br." Gzip is also handled, by content sniffing rather than extension. Both Unity compression formats therefore work on itch without Decompression Fallback.

Player Settings that matter (Edit > Project Settings > Player > Web):
- Publishing Settings > Compression Format: Brotli (smallest) or Gzip. Both fine on itch. Gzip is the Unity default and builds faster.
- Publishing Settings > Decompression Fallback: leave DISABLED (the default). Enabling it renames files to `.unityweb`, which defeats itch's extension-based Brotli detection, bloats the loader, and disables WebAssembly streaming. Unity's own deploy page says enabling it "results in a large loader size and a less efficient loading scheme."
- Publishing Settings > Data Caching: enable, so returning players skip the .data download.
- Publishing Settings > Name Files As Hashes: optional, helps cache busting.
- Resolution and Presentation > WebGL Template: Minimal, or the community "Better Minimal WebGL Template" that itch.io's own docs link to by name for Unity.
- Embed Options > Frame Options > "SharedArrayBuffer support" is an itch dashboard setting, not a Unity one. Only tick it if you enable Unity multithreading. Leave both off. itch sends COOP: same-origin and COEP: credentialless on the embed page, and Safari still needs a popup window.

Limits. The binding constraints are the HTML5 playable limits, not the upload cap:
- Extracted content total: not greater than 500 MB
- Any single extracted file: not greater than 200 MB
- Not more than 1,000 files after extraction
- Path plus filename: not more than 240 characters
- ZIP must contain index.html at the root
Upload cap itself: the web uploader accepts up to 1 GB by default (itch staff say it can be lifted to 2 GB on request); butler has no practical limit but does not change the HTML5 limits above.

Concrete problem in this project: C:\dev\dik-dik\Assets\StreamingAssets\Whisper contains ggml-tiny.bin (77.7 MB) and ggml-tiny.en.bin (77.7 MB), 148 MB total. On Web, StreamingAssets are copied into the build output and fetched by URL via UnityWebRequest, not packed into the .data file. They will ship. That is 148 MB of dead weight in a build with no voice, and it eats a third of itch's 500 MB extracted budget.

4. WEBGL2 AND UNITY 6.5 REGRESSIONS

WebGL 2.0 is required. Unity 6.5's Web graphics page: "WebGL2 is the default graphics API and is compatible with most devices and browsers." WebGL 1.0 is no longer listed as an option. WebGPU exists but the manual says it "is experimental and not recommended for production usage." Do not enable it for itch.

Things to avoid, and three found in the current build script:
- Code Optimization = Runtime Speed, and LTO. Unity issue tracker has "[WebGL] Build fails and Shader errors are logged when Code Optimisation is set to Runtime Speed." A 2026 community write-up on Unity Discussions reports the same combination breaking third-party packages that use unsafe code or unmanaged memory. whisper.unity's runtime asmdef has allowUnsafeCode true, so this is directly relevant if you ever ship a Web build with it in. Use the default.
- Multithreading / WebGL.threadsSupport: multiple open issue tracker entries for build failures and an Editor crash. It also requires COOP/COEP, which on itch means the SharedArrayBuffer checkbox and Chrome-first behaviour. Leave off.
- DikdikBuild.cs line 87, `PlayerSettings.WebGL.memorySize = 512`, is a no-op. Unity's scripting reference: "This setting has been deprecated and does not have any effect on WebAssembly builds." Use Initial Memory Size / Memory Growth Mode / Maximum Memory Size instead.
- DikdikBuild.cs line 90, `exceptionSupport = WebGLExceptionSupport.None`. Unity's default is "Explicitly Thrown Exceptions Only," and there is an issue tracker entry titled "Project build fails and errors are thrown when building for WebGL platform with Exceptions disabled." With None you also lose any diagnostic when a null reference hits in a browser you cannot attach a debugger to. Keep the default for the itch build.
- Unity 6000.5.0f1 release notes do list Web fixes (UUM-134978 WebGPU shader compiler, UUM-126250 missing malloc/free with -sERROR_ON_UNDEFINED_SYMBOLS=0), so the 6.5 line was still churning on Web. 6000.5.2f1 release notes contain no Web items. Patch releases past .2 exist (.3, .4). Nothing forces an upgrade, but if the Web build misbehaves, moving up the 6000.5.x patch line is the cheapest first move.

1. CHEAPEST STARFIELD AND PLANET
Skybox for stars, one primitive sphere for the planet. Particles and quads are the wrong tool: stars must not parallax as the camera translates, and a skybox is direction-only so it gets that for free at one fullscreen pass with no per-object cost or GC.

Two concrete blockers in the existing shader (GradientSky.shader lines 76-83):
- Stars are gated to the upper hemisphere: `if (h > 0.05)` with a `saturate(h * 2.0)` falloff. In space the camera looks sideways and down, so most of the frame would have no stars at all.
- `step(1.0 - _StarAmount * 0.02, s)` produces a hard one-cell star. Under slow cinematic rotation these crawl and alias badly. Needs `smoothstep`.

2. DRIVING THE CAMERA
Coroutine. Confirmed, and the alternatives are worse than the question assumes because neither package is installed:
- Cinemachine: `com.unity.cinemachine` is absent from both manifest.json and packages-lock.json, and it is not installed by default in Unity 6. It solves problems this shot does not have (dynamic targets, collision avoidance, gameplay blends) and would fight `CameraFollow.LateUpdate`.
- Timeline: also absent. packages-lock.json contains only `com.unity.modules.director` (the Playables runtime module), NOT `com.unity.timeline`, so `TimelineAsset` and `TrackAsset` do not exist in this project. Building a timeline from an Editor script means adding a package, creating asset plus sub-assets through AssetDatabase, and binding tracks, to reproduce what a handful of `Vector3.Lerp` calls do. Timeline's clock is also frame-driven by default, so it does not solve sync either.
- The project already has the pattern: EndingSequence.cs runs a whole multi-beat sequence in a coroutine with realtime timing and per-frame caption updates.

## 3. Guidance on retaining/replaying recorded audio, and privacy for voice interfaces

No game accessibility standard covers this. Verified negative across all four bodies:
- Game Accessibility Guidelines: no guideline on audio retention, recording, or consent. The full list has none.
- XAG 101-123: no privacy guideline. XAG 119/120 mention privacy only in the impact tables quoted above.
- APX (AbleGamers): 12 access patterns, none about data. The patterns are Flexible Controllers, Same Controls But Different, Improved Precision, Flexible Text Entry, Second Channel, Clear Channels, Distinguish This From That, Flexible Displays, Clear Text, Personal Interface, Leave It There, Do More With Less.
- WCAG2ICT ("Guidance on Applying WCAG 2 to Non-Web Information and Communications Technologies", W3C Group Note, 11 December 2025): does not address privacy at all, and mentions speech only inside the virtual keyboard definition ("eye-gaze, morse code, speech, and switches (e.g. sip-and-puff) have all been used by virtual keyboards as input"). WCAG 2 has no privacy success criteria. Citing WCAG2ICT for the discard-audio decision would be a category error.

The correct authorities are data protection and web platform privacy:

1. GDPR Article 5(1)(c) data minimisation: personal data shall be "adequate, relevant and limited to what is necessary in relation to the purposes for which they are processed". Article 5(1)(e) storage limitation: "kept in a form which permits identification of data subjects for no longer than is necessary for the purposes for which the personal data are processed". Article 25 adds data protection by design and by default. Discarding the buffer once the transcript exists is textbook 5(1)(c) plus 5(1)(e).

2. EDPB Guidelines 02/2021 on virtual voice assistants, version 2.0, adopted 7 July 2021 â€” the most on-point regulator guidance that exists for voice interfaces. It states that after executing a user's command the personal data should be deleted immediately unless there is a legal basis for further processing, that recordings made by mistake should be deleted immediately after detection, and that retaining voice data indefinitely until a deletion request is not in line with the storage limitation principle. This is directly quotable support for discard-after-transcription.

3. W3C Web Speech API (Draft Community Group Report, Web Audio Working Group): "User agents must only start speech input sessions with explicit, informed user consent"; "User agents must give the user an obvious indication when audio is being recorded"; warns that "Speech input could potentially be used to eavesdrop on users. Malicious webpages could use tricks such as hiding the input element or otherwise making the user believe that it has stopped recording speech while continuing to do so." The spec now carries a processLocally attribute for on-device recognition. This supports both the discard decision and the on-device decision, and it supports adding a visible mic-live indicator, which the game should have and which is cheap.

One honesty flag for the author. The README describes recording sound templates for non-verbal remapping (line 248: "During remapping, record any sound at all", and line 262: "Template matching on raw audio"). If the game stores those templates, it retains user audio, and the README's current claim "No network, no account, no audio leaving the machine" (line 183) is true but incomplete. Say where the templates live on disk, that they never leave the machine, and how a player deletes them. That turns a potential contradiction into a design decision.

## 4. What an HCI researcher reviewing this would expect that a hobbyist misses

Written for a PIRG/TAUCHI reader. Blunt, in rough priority order.

1. **A denominator.** "81.2% on day 1" is not a result. A reviewer needs: number of utterances, number of command classes, per-command confusion matrix, what counted as success, and false-accept separated from false-reject. Those two failure modes have opposite design consequences and collapsing them into one accuracy figure is the single clearest hobbyist tell.

2. **System version pinned.** whisper.cpp commit, model size, quantisation, sample rate, VAD settings, decode parameters. Speech results are worthless without them and are trivially cheap to record.

3. **n=1 named as n=1.** One speaker is an autoethnographic probe, not an evaluation. Framed honestly as a first-person accessibility probe it is respectable and publishable in this community; framed as a performance number it is not. Say which it is in the first sentence of the section.

4. **A baseline.** Run the same command set through a larger model, or through a second speaker, so "the model misheard my accent" is measured rather than asserted. Without a comparison the accent claim rests on the author's word, and the reviewer's job is to notice that.

5. **Ethics and data handling.** Any recorded voice, including the author's own, and certainly any future participant's: consent, storage location, retention period, deletion route, and the Tampere University ethical review path. In a Finnish/EU research group this is not paperwork, it is a competence signal. Its absence is noticed in seconds.

6. **Error recovery treated as a first-class mechanic.** Voice interfaces fail at recovery more than at recognition. What happens on a misrecognition? Is there an undo? Is there confirmation before a destructive or irreversible command? Is there a visible "I heard X" so the player can see the failure rather than infer it from the rover doing the wrong thing? A hobbyist tunes accuracy; a researcher designs for the residual error that will never go away.

7. **Latency, reported.** Time from end-of-speech to in-game action, median and tail. For a rover that has to stop before a cliff, tail latency is the design constraint, and it interacts with the "adjust game speed" guideline directly.

8. **The open-mic problem stated.** Always-on versus push-to-talk, and the gate design, with a measured false-accept rate under background speech. This is also the honest bridge to the privacy section: a gated mic is both a usability and a privacy decision.

9. **Claims scoped to the build.** Replace "each level embodies one guideline" with a three-column table: guideline title exactly as published, tier, and where in the build it is demonstrable. Add rows for "partially implemented" and "deliberately not implemented, because". 10. **Positioning against prior work.** At minimum, cite Koenecke et al. 2020 and EdAcc properly rather than as "published evaluation on the EdAcc and AfriSpeech datasets finds". 11. **Reflexivity.** The author is simultaneously the designer, the instrument, and the excluded user. Say that explicitly and say what it buys and what it costs.
